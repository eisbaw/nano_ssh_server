v31-trim optimization log
=========================
Baseline: v30-chacha at commit 5f5fe0c01fdf7da7addfb7da3676dbe013acdb13.
Both versions built locally with GCC 13.3.0 and binutils 2.42 (x86-64
Ubuntu 24.04), `CC=gcc just build <version>` (musl-gcc is not installed
here; the build is freestanding, so it emits the same bytes).  v30-chacha
is untouched; v31-trim is a separate directory.  No executable compression:
the 3,426 bytes are the image the kernel maps, byte for byte.

Result: 4,095 -> 3,426 bytes, -669 bytes (-16.3%).

Each size is the whole binary after that step, in the order the steps
were taken.  The algorithms are those of v30-chacha:
ecdh-sha2-nistp256, ecdsa-sha2-nistp256, chacha20-poly1305@openssh.com,
all 20 ChaCha20 rounds, full SHA-256, Fermat inversion, the same
double-and-add ladder on k + n.  Nothing is compressed.

Behavior changes (all from steps 1-4, 7 and 24)
------------------------------------------------
- After CHANNEL_OPEN_CONFIRMATION the server sends "Hello World" and
  CHANNEL_CLOSE at once instead of first answering the client's
  pty-req/env/shell/exec requests.  Those arrive after its CLOSE, so they
  are not answered; RFC 4254 lets a party close a channel without EOF, and
  OpenSSH prints the message and exits (status 255, as before: no
  exit-status is sent).  The server then reads until the client closes the
  connection instead of stopping after one packet.
- Only a "session" channel open is understood (the sender channel is read
  where a session open has it); OpenSSH opens one for every login.
- The version line must end in CR LF (RFC 4253 4.2 says it MUST) and be at
  most 252 bytes (RFC 4253 allows 255); v30-chacha took 255 bytes and a
  bare LF.
- The first packet is taken to be KEXINIT and a 70-byte packet after it to
  be KEX_ECDH_INIT without checking their types or the 04 point prefix.  A
  malformed one gives a transcript the client cannot verify, so the
  handshake fails at the client; the peer point was never validated (see
  README), and the arrays it lands in are sized for the largest packet.

Verification
------------
- `just test v31-trim`: version exchange, full connection ("Hello World"),
  wrong password rejected / correct accepted - all pass.
- CLAUDE.md's real-client check: `just run v31-trim`, then
  `echo "password123" | sshpass ssh -p 2222 user@localhost` prints
  "Hello World" (OpenSSH 9.6p1, sshpass 1.09), twice from one process.
- tests/test_crypto.py (new, `just test-crypto`): v29-p256, v30-chacha and
  v31-trim built as libraries and checked against Python references -
  SHA-256 for 300 lengths (0..199 and random), ChaCha20, Poly1305 (the RFC
  8439 vector, 171 keys/messages including all-0x00/0xff keys, and the
  equal / one-bit-off tag results of the compare-as-you-write path),
  2,450 field operations under p and n (edge values, unreduced
  multiplier operand, inverses), 16 scalar multiplications over the
  ladder's range and edges, 4 ECDSA signatures (formula and verification).
- tests/test_chacha.py: 365 ChaCha20 cases per version (it now drives
  v31-trim's state-template interface).
- put_mpint() against a Python mpint encoder: 20,139 values (every count
  of leading zero bytes 0..32 with top bytes 01/7f/80/ff, random widths).
- A probe script against one server process, a real login after each
  probe: banners (300 bytes without LF, bare LF, CR LF only, EOF inside
  and after the banner), packet lengths 0, 1, 4, 4093, 0xffffffec and
  0xffffffff, padding length >= packet length, a MITM proxy flipping one
  bit in the length, payload or tag of the first encrypted client packet
  (all rejected), wrong user/password pairs, a 3.5 KB exec request, a
  forced pty, ten more logins; the process is alive at the end.  The same
  probes pass on v30-chacha.
- valgrind 3.22 (memcheck): 0 errors over two logins and a rejected
  password.  Valgrind rejects the packed raw image (its header fields
  hold program data), and the linked .elf only exists for nm/objdump (its
  one segment sits at file offset 0x100, which neither the kernel nor
  valgrind maps correctly), so it ran on the same objects relinked with a
  page-aligned segment - whose loaded bytes are the shipped 3,426-byte
  image, byte for byte.  No heap is used; the "switching stacks" warning
  is die() resetting the stack.
- Nine timed logins on this machine: median 0.65 s (v31-trim) against
  0.80 s (v30-chacha), probably mostly because the channel phase no longer
  waits for the client's requests.  A small sample, not a benchmark.
- Nix itself was not available locally, so the Nix CI toolchain was not
  reproduced here; the byte counts above are for GCC 13.3.0/binutils 2.42.

Compiler flags
--------------
Every flag change was found by a greedy sweep (213 candidate
-f/-m/--param flags to add, each current flag to remove, one at a time,
repeated until nothing helped), and a flag was only
taken if the resulting binary still passed a real OpenSSH login, correct
and wrong password, exec and no-tty sessions.  That test is what rejected
-fcall-saved-rdi (-7 bytes): it makes GCC restore rdi in the epilogue of
keygen() after loading the argument of its tail call, so the server
segfaults at startup.  Two further sweeps at 3,484 and 3,426 bytes found
nothing.

Measured alternatives rejected
------------------------------
- memcpy() as rep movsb at every call site (measured at 3,512 bytes):
  +13.  It pays only at the sites kept inline; at the final build the
  others cost send_chan +37, the ladder +2, ChaCha's working copy +7,
  SHA-256's per-block state copy +29, the key derivation's first copy +3.
- aead() as straight-line code instead of the two-pass loop (at 3,494): +22.
- A static Poly1305 key buffer instead of the stack one: +3.
- The Poly1305 tag loop as an adc chain in inline asm (the carry saved
  with sbb/add around the compare): 0 to +4.  (lahf/sahf would save it in
  two bytes but is not baseline x86-64.)
- Poly1305 tag position taken from the end of the message: +4 (C) or 0.
- cfd as a global register variable: -2, but needs -ffixed-<reg> for
  every translation unit under LTO; not taken.  -ffixed-r9..r15/rbp
  alone: +4 to +48.
- 32-bit address arithmetic or a base register in the interpreter's
  operand decode: +1 to +4.
- Not tried: aes128-gcm@openssh.com on AES-NI/PCLMULQDQ might make the
  cipher smaller, but needs CPU extensions beyond baseline x86-64.

Trade-offs
----------
The string-instruction loops (rep movsb/stosb/scasb, lodsb/stosb with the
direction flag flipped around each store, lodsl/bswap/stosl) are small but
not fast; they run on short buffers here and the bit-serial P-256
arithmetic still dominates a login.  The inline asm is confined to
statements inside C functions with exact register constraints.  No new
runtime dependency, no new buffer (rep[] is the same 512 bytes, its first
45 now the image's last 45), and no change to the cryptographic algorithms
or their constant-time properties (the Poly1305 check still ORs all 16
byte differences).
