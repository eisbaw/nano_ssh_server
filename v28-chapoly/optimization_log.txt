v28-chapoly optimization log
============================
Baseline: v27-onecurve, rebuilt in the same environment for a fair comparison
(gcc 13.3, binutils 2.42, Ubuntu 24.04 x86-64): 9,946 bytes - identical to
the number v27-onecurve's own log records.

The theme is the one v27-onecurve's log left as "not attempted": the packet
cipher.  aes128-ctr + hmac-sha2-256 cost ~950 bytes (S-box, key schedule,
rounds, CTR, HMAC wrapper).  chacha20-poly1305@openssh.com needs a ChaCha20
stream (~300 bytes) and a Poly1305 tag - and Poly1305 is h = (h + c) * r
mod 2^130-5, which is exactly the generic modular arithmetic fprime.c already
provides for the Ed25519 scalar field.  So the tag costs a second modulus (built
in place from three constants) and ~330 bytes of glue, and the AES core and HMAC are gone.
Once the fprime routines are the workhorse, the same "reuse what is linked"
argument reaches the SHA constant generator, the field normalization, the
scalar reduction and the field inverse, and the rest of the steps are byte
golf on the protocol code.

Every step was measured; where several independent steps were tried in
parallel against the same base and then applied together, the table gives
the measured size after the group and the individual deltas in brackets
(they do not always add up exactly: inlining decisions shift a little).

Verification after every step with the real OpenSSH client (9.6p1):
  sshpass -p password123 ssh -p 2222 user@localhost  ->  "Hello World"
plus a wrong-password rejection and a second connection to the same server
process.  Full suite: tests/run_tests.sh v28-chapoly -> 3/3 PASSED.
Steps 1, 5, 8 and 9 change the packet crypto, the hash constants and the
field arithmetic, so the final binary was additionally checked with a
50-connection run against one server process (each connection draws fresh
X25519 and Ed25519 randomness, the client verifies the host-key signature,
and every packet is authenticated by Poly1305): 50/50 passed.

Rejected / no-effect experiments:
- Constant generator on byte arrays with fprime's raw_add()/shift_n_bits()
  (shift-and-add over the candidate's bits): 0 - the memsets ate the gain;
  step 5's fprime_mul() form is the one that pays.
- Rolling 16-word SHA-256 message schedule (as sha512_block uses): +32,
  before and after step 6.
- One SHA-2 compression function for both hashes (64-bit words masked to the
  width, rotation amounts from a 12-byte row, 48 + w/2 rounds): the core
  came out the same size as the two it replaced, and the 64-bit SHA-256
  context cost ~70 bytes in init/update/final.  +56.
- sha256_final() feeding its padding through sha256_update(): 0 (twice).
- derive() noinline: +32.  aead() noinline: 0.
- Host-key blob built inside the KEX reply and hashed from there: 0.
- Signature written straight into the reply: 0.  ChaCha state set up by one
  loop instead of two memcpy(): 0.  Tighter put_mpint(): 0.
- K's mpint encoded once for the exchange hash and the derivation: +32.
- Flags: inherited from v26/v27 (-Oz, single-invocation LTO, tiny.ld,
  SUBALIGN(1), sstrip.py); no new flag helped.
- UPX/compression: forbidden by project rules (and pointless for the in-RAM
  footprint this project actually targets).

Cost of the changes, honestly stated:
- Startup.  The SHA constants are now generated with 208-iteration
  shift-and-add multiplies (about 10,000 of them): the server takes 0.3-0.5 s
  to reach listen() on this machine, against ~15 ms for v27-onecurve.  The
  project's test scripts wait 2 s / 5 s before connecting.
- Speed.  Poly1305 runs bit-serially through fprime_mul() (~1-2 MB/s), the
  SHA-2 rounds shift an array instead of renaming registers, and the field
  inverse is a full square-and-multiply with a multiply on every bit.  A
  handshake is still well under a second; all of this only makes sense
  because the target is code size.
- Interoperability.  The server offers exactly chacha20-poly1305@openssh.com
  and sends empty mac name-lists (an AEAD cipher carries its own MAC, and
  OpenSSH skips MAC negotiation for it); a client that insists on a non-empty
  mac list, or that lacks the OpenSSH AEAD, cannot connect.  USERAUTH is
  accepted only as the exact message OpenSSH sends for user "user" /
  password "password123" over service "ssh-connection"; v27 ignored the
  service name.  Received packets must fit 512 bytes after NEWKEYS (the
  KEXINIT buffer is still 4 KB).
- Inherited from v27-onecurve: no on-curve check of the peer's X25519 point,
  randomised (getrandom-based) Ed25519 signing.
