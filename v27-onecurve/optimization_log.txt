v27-onecurve optimization log
=============================
Baseline: v26-genk, rebuilt in the same environment for a fair comparison
(gcc 13.3, binutils 2.42, Ubuntu 24.04 x86-64): 12,074 bytes - identical to
the number v26-genk's own log records for musl-gcc, because -nostdlib
-ffreestanding links nothing from either libc.

The theme is that v26-genk carried two complete Curve25519 implementations:
the c25519 Montgomery ladder for the key exchange and the twisted-Edwards
group law for the host-key signature. They are the same group in different
coordinates, so one of them is redundant - and once the mapping between them
is in place, a square root is linked anyway and several other duplications
collapse with it.

Verification after every step with the real OpenSSH client:
  sshpass -p password123 ssh -p 2222 user@localhost  ->  "Hello World"
plus a wrong-password rejection and a third connection to the same server
process.  Full suite: tests/run_tests.sh v27-onecurve -> 3/3 PASSED.

Steps 9 and 11 change the core group arithmetic, so both were additionally
checked with a 50-connection stress run against one server process (each
connection draws a fresh ephemeral X25519 key and a fresh Ed25519 nonce, and
the OpenSSH client verifies the host-key signature and agrees on the shared
secret, so ~40,000 random point operations are covered): 50/50 passed.

Rejected / no-effect experiments:
- Recovering the Ed25519 base point's x from its y with the square root that
  is now linked: saves 32 bytes of table but costs ~130 in the normalize/
  negate/select needed to pick the even root.  +96, reverted.
- Deriving d = -(121665/121666) at startup: 32 bytes of table for ~62 bytes
  of f25519_load/f25519_neg.  +32, reverted.
- Rolling 16-word SHA-256 message schedule (as sha512_block uses): +32.
- Marking put_str() noinline: no change.
- Flag sweep - no effect from -fno-jump-tables, -mgeneral-regs-only,
  -mno-sse, -falign-functions=1, -fconserve-stack, -fno-tree-vectorize,
  -fweb, --param=inline-unit-growth=0, -flto-partition=one,
  -fno-early-inlining, -fno-partial-inlining.  Actively worse:
  -fno-toplevel-reorder (+1,584), -fno-inline-small-functions (+320),
  -fno-ipa-cp (+192), -fno-tree-loop-optimize (+128), -fno-ipa-icf (+96).
- UPX/compression: forbidden by project rules (and pointless for the in-RAM
  footprint this project actually targets).

Not attempted, as a note for a future version: replacing aes128-ctr +
hmac-sha2-256 with chacha20-poly1305@openssh.com would drop the AES core and
the HMAC wrapper (~950 bytes) for a ChaCha20 permutation and a Poly1305
(~600 bytes), at the cost of the AEAD's two-key packet framing.

Cost of the changes, honestly stated:
- Speed. The Edwards ladder needs ~16 field multiplies per bit against the
  Montgomery ladder's ~10, doubling now uses the 9-multiply addition law
  instead of the 7-multiply dedicated formula, and the addition law runs
  through an interpreter. A handshake is still well under a second here, but
  this trade only makes sense because the target is code size.
- A peer u-coordinate on the quadratic twist has no square root on the
  curve, so it produces a wrong shared secret and the handshake fails at the
  first MAC check, where the Montgomery ladder would have carried on. Real
  SSH clients never send twist points.
- Signing is randomised rather than deterministic, so it depends on
  getrandom(2) for every signature, not just for key generation.
