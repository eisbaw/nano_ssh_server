v29-p256 optimization log
=========================
Baseline: v28-chapoly, rebuilt in the same environment for a fair comparison
(gcc 13.3, binutils 2.42, Ubuntu 24.04 x86-64): 7,975 bytes - identical to
the number v28-chapoly's own log records.

The theme is the last duplication v28-chapoly left standing.  Its handshake
needed two curves - Curve25519 for the key exchange and Ed25519 for the host
key, which v27 had already folded onto one group law but which still needed
the Montgomery<->Edwards mapping, a square root and a dedicated 2^255-19
field with its own carry folding - and two hashes, because the Ed25519
challenge is SHA-512 while everything else in the handshake is SHA-256.
NIST P-256 serves the key exchange (ecdh-sha2-nistp256) and the signature
(ecdsa-sha2-nistp256) in one coordinate system, and ECDSA hashes with
SHA-256, so with P-256 the SHA-512 core, the 2^255-19 field code, the
square root and the curve mapping all go.  What is left of the public-key
crypto is one generic modular multiplier (fp.c: shift-and-add, any 256-bit
modulus) and one short-Weierstrass double-and-add program; the multiplier
also runs the group-order arithmetic of ECDSA and, as in v28, Poly1305.

Every step was measured; where several independent steps were explored in
parallel against the same base and then applied together, the table gives
the measured size after the group and the individual deltas, as measured
against that base, in brackets (they do not add up exactly: inlining
decisions shift a little, and .text savings only reached the file in
32-byte quanta until step 8).

Verification after every step with the real OpenSSH client (9.6p1):
  sshpass -p password123 ssh -p 2222 user@localhost  ->  "Hello World"
plus a wrong-password rejection and further connections to the same server
process (20-40 per step), and after steps 9-12 the crafted-length and
truncated-banner probes (the server must keep serving).  Full suite:
tests/run_tests.sh v29-p256 -> 3/3 PASSED.  The crypto core is additionally covered by a native unit test
(SHA-256 vectors including the padding boundaries, the RFC 8439 Poly1305
vector, P-256 scalar multiplication and ECDSA against a Python reference,
and the edge scalars of the ladder) and, at the baseline, by an
independent differential fuzz of fp.c/p256.c against big-integer
arithmetic (320,800 field cases, 700+ curve cases, 354 Poly1305 cases, no
mismatch), a protocol review and a live malformed-input fuzz.

Cost of the changes, honestly stated:
- Speed.  Every field operation runs on the bit-serial generic multiplier
  (~250 K instructions per P-256 multiplication) and the projective ladder
  needs 22 of them per scalar bit: a handshake takes ~0.6 s of server CPU
  on this machine against ~0.07 s for v28-chapoly, and startup (one scalar
  multiplication for the host key) ~0.2 s.  On a microcontroller this
  scales accordingly; the trade only makes sense because the target is
  code size.
- Tooling.  The file is a raw image, not a well-formed ELF for tools:
  `file` and readelf see the ECDSA program where e_ident's data-encoding
  and version bytes belong and garbage in p_align (the kernel reads
  neither).  nano_ssh_server.elf, the linked file, keeps the symbols for
  nm/objdump.  Building needs objcopy (binutils) and no longer python.
- Interoperability.  The server offers exactly ecdh-sha2-nistp256,
  ecdsa-sha2-nistp256 and chacha20-poly1305@openssh.com (with empty mac
  name-lists, as v28); a client without P-256 support cannot connect.  The
  KEX_ECDH_INIT must carry an uncompressed 65-byte point, USERAUTH is
  accepted only as the exact message OpenSSH sends, SERVICE_ACCEPT echoes
  whatever service the client asked for, and the client's NEWKEYS is
  awaited before ours is sent (OpenSSH sends its own as soon as it has the
  reply).  Received packets must fit 512 bytes after NEWKEYS.
- Security, beyond what the README lists for every version: no range or
  on-curve check of the peer point; scalars uniform over [2^224, n) rather
  than [1, n); a cmov-selected pointer in fp_mul (a cache-timing channel);
  the four exceptional ladder scalars are unreachable but nothing checks r
  or s for zero (probability 2^-256).  See the README's Security section.
